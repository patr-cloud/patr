# runners/common/CLAUDE.md

The shared runner framework: the `RunnerExecutor` trait, `Runner<E>`, its controller and upstream WebSocket loops, local SQLite state and reconciliation. See `runners/CLAUDE.md` for the cross-cutting picture.

## Implementing an executor

- Implement `RunnerExecutor` (`src/executor.rs`). `initialize()` connects to the backend once and returns the executor itself, which is cloned into every loop and reconcile, so keep clones cheap (handles behind `Arc`).
- **The framework reconciles owners, not commands.** An `Owner` (`Deployment(id)`, `ManagedUrl(id)`, `System`) is the unit of work. For each owner the controller builds `expected(owner, &LocalState, &inputs)` (pure: an `ExpectedGraph` of objects and their dependencies, which never cross owners), reads `list(Some(owner))`, applies every object whose `patr.specHash` differs (dependencies first, a failed object blocks only its dependents), then deletes what's no longer expected (dependents first, skipping what's `in_use`).
- **The spec hash is the framework's.** It's `sha256(SPEC_VERSION ++ json(spec) ++ sorted (dependency id, dependency hash))`, so a changed dependency re-applies its dependents. Late-bound values (secret values, image names, config IDs) are resolved in `apply`, never in `expected`. Bump `SPEC_VERSION` when how objects are applied changes.
- **Ownership lives on the object**, as labels: `managed-by=patr`, `patr.owner`, `patr.specHash`. Objects without a valid `patr.owner` are ignored, never reaped. One runner per Docker host: a replacement runner takes over and reaps the previous one's objects.
- **Finalizers gate deletes.** An object `finalizers()` lists isn't deleted until each finalizer is done, and while its owner still expects anything, it isn't deleted at all (a volume whose path was removed keeps its data). Progress is persisted in `object_finalizer` (typed: `finalizer`, `state` and `last_error` are CHECKed enums, and `last_error` is a kind, never text), so a crash resumes it: `running` rows are reset to `pending` when the controller starts. Finalizers must be idempotent. The one kind today, `volume`, asks the API for the deployment (`GetDeploymentInfo`): a 401/404, or a 200 naming another runner, is done; a 200 naming this runner fails it, and a later reconcile retries.
- An `Err` from `apply` marks the owner failed: it's retried with backoff (1s → 5min) and its deployment reads `Errored`.
- Import surface is the prelude: `use common::prelude::*` (trait, `Runner`, `RunnerError`, config, `DatabaseType = sqlx::Sqlite`, `sqlx::{query, Row}`).

## Gotchas

- **Data access uses the compile-time-checked `query!` macro** (the prelude's, from `macros`), against SQLite. `sqlx.toml` points the macros at `RUNNER_DATABASE_URL` (the api's use `DATABASE_URL`) and maps the TEXT UUID/enum and `u16` INTEGER columns to their Rust types per table — **a new column of one of those kinds needs a line there**. The offline cache is `runners/common/.sqlx/`, regenerated by `just prepare` against `target/runner.db` (`just runner-db`).
- **Migrations and the schema DDL in `db/` use runtime `sqlx::query()`, never `query!`** — the schema is mid-change. Migrations self-register via `inventory`, take `(&mut DatabaseConnection, &RunnerSettings<()>)` (the `init_db` example passes a placeholder), and the DDL + bookkeeping insert must happen in **one transaction** (partial DDL leaves `*_new` temp tables that wedge retries).
- **Tests:** `cargo nextest run --package common`. `managed_mode::` tests are forced single-threaded (`.config/nextest.toml`) — they share one real HTTP test server on **fixed port 3000**. Non-managed tests get isolated temp SQLite and run in parallel.
- **FullResync diffs** (`src/runner/websocket.rs`): it fetches everything first, outside any transaction (`ListDeployment` filtered server-side by `runner`, `GetDeploymentInfo` per ID, managed URLs, secrets), then writes only the differences in one short transaction. Any failed call (429 and 5xx included) aborts it with SQLite untouched, so a failure never reads as "deleted". Runs on every WS (re)connect and on a timer. Write order matters: removed deployments (their managed URLs go with them) before upserts, and a deployment's probes are nulled before its `deployment_exposed_port` rows go (they FK each other both ways).
- **Intent and observed status are separate columns**, mirroring the API. `deployment.should_run` is the API's intent; `deployment.observed_status` (nullable) is written only by the runner. Upserts and resyncs set only the desired columns (`ON CONFLICT DO UPDATE SET` never names `observed_status`), and a delete takes it with the row. The runner sends a deployment's observed status upstream (`SendStatusUpdate`) whenever it changes, and every one of them after each resync, which catches the API up on whatever it missed while disconnected. The API drops the connection when it fails to store one, so the reconnect's resync sends it again. The runner never sends `Stopping` or `Unreachable`.
- **Migrations recreating `deployment` defer foreign keys** (`PRAGMA defer_foreign_keys = ON`, see `m007`): `PRAGMA foreign_keys = OFF` is a no-op inside the migration's transaction, and every child table references `deployment`. Copy it aside, drop it, recreate it under its own name, then re-insert — renaming a `*_new` table into place leaves the violations standing at commit.
- **Loops** (`src/runner/`): `Runner::run` creates the channels and joins two loops on them: the controller and the WebSocket connection (a failed connect is retried with backoff, 1s → 60s). The controller's queue of owners is `pending`/`in_flight`/`dirty`, 4 at a time, `System` first. Owners are queued by:
  - upstream changes;
  - `watch()`, one event per changed owner, ignored while the owner is in backoff;
  - `Wakeups`: retries with backoff, and rechecks, 5s while a deployment reads `Deploying` or `observe` failed (no backend event reports a task failing to start), 30s while an object waits to be deleted;
  - a full reconcile every 10 min, or right away when the watch stream ends, since events may have been missed.

  After a deployment's reconcile, it records `observe(id)` (`Errored` if the reconcile failed) in `deployment.observed_status`, and sends it upstream if it changed. A change to any non-`System` owner re-enqueues `System`, because the ingress mounts the other owners' routes.
- **Loop rules**, which no framework enforces:
  - Each loop owns its state. No maps or locks are shared across tasks.
  - Loops wake each other over the channels, never `Notify`.
  - Each loop waits on one `future::select` of its `sleep_future` and its channels (or streams). The sleep comes back in the losing half (`pending_sleep`) and is kept; everything else in it must be cancel-safe (`recv()`, `stream.next()`).
  - Retries never sleep inside a handler: the controller's reconciles are tasks that message it back, and its retries and rechecks are deadlines in `Wakeups`, one stream over a single sleep. A loop sleeps in place only when what it serves is gone: the WebSocket loop before reconnecting. The controller watches the backend again through a stream that waits first, so it never blocks.
  - Every await that can take a while (the `select`, connecting, a resync, a server message, a retry wait) goes through `.with_cancel_check()` (`utils/ext_traits.rs`), so the exit signal doesn't wait on it. It returns `RunnerError::ExitSignalReceived`, which is why each loop returns `Result<!, RunnerError>` and uses `?` only on it.
  - An error is logged with its cause and handled in the loop. A loop returns only once `GLOBAL_CANCEL_TOKEN` is cancelled, and a reconcile that panics counts as a failed one.
- **`Runner::run` connects and resyncs before starting the loops.** `websocket::connect` opens the connection (10s timeout) and sends the handshake straight away, since the API streams nothing and shows the runner offline until it has one. `Runner::run` then resyncs on it and sends every observed status. On a fresh database (`db::initialize` reports whether it created it) it retries both until the resync succeeds, because until then the database expects nothing and the controller would reap every object on the host. An existing database tries once and starts from what it has. `websocket::run` takes that connection, and resyncs it on its timer; every connection it opens itself is resynced right away, so each connection gets exactly one resync up front.
- `db::initialize` (migrations) runs **before** `E::initialize`. `run()` joins the loops, which return only once the exit signal cancels `GLOBAL_CANCEL_TOKEN`, with `ExitSignalReceived`. That exits with code 0; any other error is returned, so the process exits non-zero and systemd restarts it, as it does when a loop panics. rustls' crypto provider is installed manually in init because ring + aws-lc-rs are both linked.
